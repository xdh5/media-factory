# 发布韩语视频

使用 `publishing` MCP，传 `business_line="language_learning"`、`content_kind="en-ko"`，由 MCP 同时选择原版与问答版。产物查找、R2 恢复、去重、账号路由和记录写入交给 MCP，不直接运行发布脚本。

## 用户信息与默认时间

- 必须明确产物计划发布日期 `publish_date`，不能默认今天或根据当前目录猜测。
- 账号组与平台必须明确，并通过 `publishing_list_account_groups` 核实，传 `business_line="language_learning"`、`account_group="korean"`，使用默认摘要。韩语成片的账号组名称是 `korean`。
- 用户只指定某天发布时，以该日北京时间 16:00 为目标；尚未到该时刻则预约，已到或超过则立即发布。
- 用户明确指定其他具体时间时遵从其要求；明确要求现在发送时立即发布。

## 执行与交付

1. 先调用 `publishing_list_account_groups`，同时指定本次 `platforms`。有账号需要登录或检测失败时立即提示并展示可用的登录入口，处理完成后重新预检。只有 `all_accounts_ready=true` 才先用醒目粗体通知“**全部账号已登录，开始发布**”，再自动继续，无需用户确认。账号未全部通过前不恢复成片或发布。随后调用 `publishing_preview`，检查待发布的原版、问答版及数据库重复项。没有可发布内容时说明原因并停止。
2. 多日期发布使用共享的 `publishing_start_batch` 一次提交；`publications` 每项填写 `publish_date`、`content_kind="en-ko"` 及按上述规则确定的 `publish_mode`、`publish_at`。返回批次路径后后台程序独立执行，宿主持续等待并按下述规则盯进度，不能直接结束对话让用户反复催问。单日交互诊断仍可用 `publishing_start_publish` 和 `publishing_poll_task`。完整明细仅在诊断时读取。
3. 登录检测失败时按 MCP 返回值恢复。抖音、快手、头条或视频号需要扫码时，调用登录工具；二维码不能只留在工具输出，必须用 `qr_path` 展示 Markdown 图片并附可点击文件链接。轮询扫码成功后重新预检再发布。
4. 展示逐平台成功、预约或失败结果，不重复手工入库。
5. 查找工具时只筛选 `publishing` 名称，先输出名称，再读取所需工具说明，不输出其他业务线的工具描述。

## 持续观察发布

- 每次发布都持续盯进度，直至本次范围全部完成、用户明确叫停，或确实需要用户处理；韩语和财经均适用。不要把针对 GitHub 制作的“不用监视”沿用到发布任务。
- 正常发布每 3 分钟调用一次 `publishing_batch_status`，只读摘要并简短汇报已确认成功数、当前日期及平台；即使没有变化也说明当前等待环节。等待使用不消耗模型生成的等待工具，不用密集调用或长篇后台对话；每次阻塞等待不超过 60 秒，累计到 3 分钟再查询。
- 一旦返回验证码、登录失效或平台限制，立即提醒并展示可用窗口、二维码或授权入口。发布中不要为重复检查登录启动竞争同一账号组的浏览器；优先读当前任务状态。
- 状态停滞一轮时检查对应任务的页面或最新日志，区分上传缓慢、转码、验证码和进程退出，不能只反复报“运行中”。已有上传仍在推进时不重启任务；结果不确定的提交先核对平台回执，不盲目重传。
- 完成后核对逐平台回执再汇报；需要用户处理时明确指出阻塞原因和操作入口，处理后继续同一范围。不要自动建立定时自动化代替本轮等待。
